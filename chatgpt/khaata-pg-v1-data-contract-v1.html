PG V1 Data & Event Contract

Source-backed invariants translated into an implementation model. Proposed storage shapes are explicitly marked so they are not mistaken for frozen product decisions.

What is frozen: product semantics, lifecycle boundaries, money invariants, history preservation and offline/sync constraints.
What is proposed here: table/entity names, field names, event envelopes and relationship shapes. These are implementation scaffolding, not source-of-truth product decisions.

Names below are chosen for implementation clarity. The distinctions they encode are source-backed; the exact storage shape is proposed.

Relationship map

The goal is to avoid accidental “one record does everything” designs.

business ├─ property_node* │ └─ occupancy_assignment* ├─ tenancy* │ ├─ tenancy_role_assignment* │ ├─ rent_term* │ ├─ occupancy_assignment* │ ├─ obligation* │ │ └─ payment_allocation* │ ├─ charge* │ ├─ financial_adjustment* │ ├─ payment_promise* │ └─ security_account │ └─ security_event* ├─ payment* │ ├─ payment_allocation* │ └─ receipt_snapshot ├─ expense* ├─ cash_custody_event* ├─ approval_request* └─ staff_access*
Do not store “current room” as the only occupancy truth. Derive it from active occupancy assignment.
Do not store “balance” as the only financial truth. Derive it from obligations, allocations, adjustments, security applications and credits.
Do not store “deposit” as one number. Preserve agreed amount, actual deposit events, actually held amount and ownership/source.
Do not store staff cash as a tenant receivable. Custody is downstream of a valid payment.

IDs, offline and sync

The product explicitly requires offline-safe identity and conflict preservation. Exact protocol remains implementation work.

Every syncable record/event gets a globally unique ID generated offline.
Legitimate concurrent events are preserved; conflicts are surfaced rather than silently overwritten.
Core operational writes must succeed locally without live server availability.
Permission to act and ability to view already-cached data offline are separate concerns.
Entitlement state may be cached as a last-verified snapshot; feature code checks entitlement keys, not tier names.
Implementation suggestion: use immutable event IDs plus per-record version metadata rather than “last write wins” for financially or operationally meaningful records.

Hard invariants

Violating one of these should fail tests, not merely show a warning.

An Upcoming tenancy cannot become Active without explicit Confirm joined.
A past joining date cannot auto-cancel or release the bed.
Room transfer cannot overwrite prior occupancy history.
Room transfer cannot silently change rent.
End tenancy cannot erase financial follow-up or pending refund.
Posted payment/receipt history cannot be edited in place.
Security cannot automatically settle arrears.
Write-off, waiver, discount and dispute cannot be represented as payment.
Cash discrepancy cannot reopen a tenant obligation that was validly paid.
Approval cannot be treated as proof that the approved action executed.
Historical staff attribution must survive staff deactivation/removal.
Capacity with history cannot be hard-deleted.
