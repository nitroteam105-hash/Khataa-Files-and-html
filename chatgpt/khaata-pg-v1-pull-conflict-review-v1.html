Pull + Conflict Resolution v1

The sync architecture now has the inbound half: remote application, checkpointing, explicit semantic conflicts, and resolution history.

Important fix: immutable financial/event rows are no longer updated just to say “synced”. Server version and sync state move to sync_entity_state.
No silent winner: semantic overlaps are preserved as explicit conflicts. Same-bed conflicts keep both legitimate commitments intact.

Pull transaction

read checkpoint ↓ fetch remote page ↓ BEGIN SQLite transaction ↓ dedupe remote_event_id ↓ append-only / safe mutable / semantic merge policy ↓ apply OR create conflict ↓ record remote event applied ↓ advance checkpoint ↓ COMMIT Failure before COMMIT → rollback data + checkpoint together

Merge classes

ClassBehavior
Financial/history eventsAppend only; never rewrite to mark sync status.
Safe mutable recordsVersion-aware merge; local-pending overlap becomes conflict.
Tenancy / rent / occupancySemantic validation before merge.
Unknown policyCreate conflict instead of guessing.

Bed conflict

remote occupancy overlaps same bed ↓ create bed_commitment_overlap ↓ preserve both commitments ↓ resolve the actual business situation: • change upcoming room / bed • change joining date • change / cancel planned move-out • cancel upcoming tenancy ↓ new domain command commits + syncs ↓ mark conflict resolved by domain action
Generic “local wins” / “remote wins” is intentionally unavailable for bed conflicts. The frozen PG model requires a real underlying change rather than a technical overwrite.
