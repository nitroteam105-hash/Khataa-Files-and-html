Server Change Feed + Mobile Appliers v1

The pull coordinator now has an actual server stream to read and concrete typed SQLite mappings to apply.

End-to-end pull path: typed server domain RPC → sync change feed → after-cursor fetch → semantic merge policy → typed SQLite applier → checkpoint commit.
Transport ≠ business history: the change-feed cursor exists only for synchronization ordering. Khaata's domain events and immutable financial records remain the business/audit truth.

Server publication

typed domain RPC ↓ validate + mutate server domain ↓ typed publish_*_change(...) ↓ append sync_change_feed ↓ same PostgreSQL transaction commits If any step fails → domain mutation + feed row both roll back

Mobile pull

last SQLite cursor ↓ pg_fetch_changes(after_cursor) ↓ ascending server feed rows ↓ PullCoordinator: • dedupe remote_event_id • semantic conflict check • version policy ↓ RemoteChangeAppliers: • immutable INSERT OR IGNORE • mutable typed UPSERT ↓ record applied_remote_event ↓ advance checkpoint ↓ COMMIT

Why typed publishers and appliers

The server does not dump arbitrary table rows blindly, and the phone does not dynamically construct SQL from JSON keys. Each entity has an explicit transport payload and an explicit SQLite mapping. This keeps schema changes reviewable and prevents synchronization from becoming an unrestricted mutation channel.
