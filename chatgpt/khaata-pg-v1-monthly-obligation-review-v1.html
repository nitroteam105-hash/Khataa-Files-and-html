Monthly Obligation Engine v1

This hardens the rent generator so effective-dated terms, tenancy boundaries and prepaid/postpaid timing behave deterministically.

New in this file: one effective rent term is selected for each calendar period, tenancy start/end bounds are respected, due dates follow prepaid/postpaid timing, and the deterministic key remains rent:<tenancyId>:<periodStart>.
No invented proration: the current frozen PG sources define monthly calendar billing but do not define a mid-month proration formula. This implementation therefore does not silently introduce one.

Generation path

eligible tenancy ↓ first eligible calendar month ↓ for each month through tenancy end / requested horizon ↓ find effective rent term overlapping that period ↓ already has deterministic obligation? ├─ yes → skip └─ no ↓ choose amount from effective term ↓ compute due date prepaid → billed month postpaid → following month ↓ create rent obligation + domain event + sync outbox/entity state ↓ COMMIT

Prospective rent changes

A rent change is represented by a new effective-dated rent_term. Already-created historical obligations remain untouched. For a monthly period where more than one term overlaps, the engine chooses the term with the latest valid_from so it never creates duplicate rent obligations; the overlapping-term inconsistency can still be surfaced as a semantic conflict elsewhere.

Database hardening

SQLite now additionally enforces one rent obligation per tenancy/month and rejects direct rewrites of the core identity, period or amount of an already-posted rent obligation. Financial correction should happen through explicit adjustment/correction history instead.

Mid-month charging policy remains an explicit product gap, not an implementation assumption. If later real PG usage requires prorated first/last months, that should become a deliberate rule with rounding and due-date semantics before code changes.
