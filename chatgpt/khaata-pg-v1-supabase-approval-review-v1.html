Supabase Approval Orchestration v1

The corrected local approval flow now has a matching server authority, audit and sync implementation.

New in this file: idempotent request creation, explicit approver authority, approve/decline RPCs, one-use authorizations, canonical owner attribution, append-only decision history and change-feed propagation.
Core invariant: requesting approval does not execute the protected action. Approving does not execute it either. Execution remains a separate retry of the original typed command.

Complete approval lifecycle

protected command needs approval ↓ create/reuse approval request ↓ COMMIT request only ↓ owner / authorized approver decides ↓ approve: request → approved + one-use authorization + append-only decision event ↓ requesting device pulls authorization ↓ retry original protected typed RPC ↓ validate actor + action + target + expiry ↓ perform business mutation + consume authorization ↓ COMMIT atomically

Owner attribution

Owner approval is recorded using decided_by_user_id. A staff-membership ID is optional because the sole owner is allowed to operate without a staff membership. This avoids falsely attributing an owner decision to the requester or another staff member.

Approver authority

An active staff membership alone is not approval authority. Non-owner staff must have approve_requests = Allowed. The permission itself does not recurse into another approval.
