Supabase RLS + Sync Server Contract v1

The local access, visibility and sync rules now have a proposed server-side enforcement layer.

Server rule: Supabase does not trust the mobile AccessGate by itself. Business scope, membership, visibility, action permission, entitlement and sync idempotency are rechecked server-side.
Not applied: this is a review migration. It intentionally stops before implementing generic payload-to-table mutation; production sync operations must dispatch to typed domain RPCs.

Server request path

SQLite outbox ↓ authenticated Supabase request ↓ business access check ↓ cloud_sync entitlement key ↓ action permission ↓ operation_id already seen? ├─ yes → return prior result └─ no ↓ base version conflict? ├─ yes → preserve client payload + create conflict └─ no → typed domain RPC dispatch ↓ validate invariant again ↓ append/write server domain state ↓ record idempotent ACK

Why RLS alone is not enough

RLS is naturally row-oriented. Khaata also needs field-level visibility such as “tenant record visible but balance hidden”. The proposal therefore uses RLS for business/row scope and safe security-definer read RPCs for controlled field redaction. The mobile query guard remains useful for offline UX, while the server independently enforces the same boundary.

Entitlements

The migration uses has_entitlement('cloud_sync'). It contains no Free/Pro/Premium condition. The effective entitlement snapshot is assumed to be computed from server configuration, so packaging can change without changing feature code.

Important remaining server work

The generic sync envelope deliberately does not execute arbitrary SQL. The next server build should implement typed RPCs for the highest-risk operations first: record payment, payment reversal, room transfer, security application/refund, cash handover, and end tenancy. A dedicated drain authorization mechanism is also still needed so legitimate pre-expiry outbound events can finish syncing after entitlement loss.
