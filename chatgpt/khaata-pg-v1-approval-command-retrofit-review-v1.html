Approval Command Retrofit v1

This wires the corrected approval model into the actual protected-command execution pattern.

New in this file: a shared approval-aware command runner, stable request idempotency keys, explicit approver authority, canonical owner attribution and a retrofit map for all protected PG commands.
Critical fix: a command that needs approval returns approval_required normally. It does not throw after creating the request, so the request is no longer rolled back with the transaction.

Corrected behavior

StageImplementationGuarantee
Needs approvalReturn result; do not throwRequest transaction commits
Repeated tapReuse request_keyOne pending request per command intent
ApproveCreate one-use authorization onlyNo business mutation
ApproverOwner or approve_requests=AllowedActive staff alone is insufficient
Owner auditUser ID + nullable membershipNo false attribution
Approved retryMutation + event + consume authAll atomic

Needs-approval path

protected command ↓ BEGIN SQLite transaction ↓ AccessGate.evaluate(...) ↓ Needs approval ↓ create or reuse approval_request ↓ return approval_required ↓ COMMIT No exception. No business mutation. Request survives.

Approved execution

same command retried + approvalAuthorizationId ↓ validate actor + action + target + unused ↓ perform real domain mutation ↓ append real domain event ↓ consume authorization ↓ COMMIT If mutation fails: rollback mutation + consumption together

Approver authority

An approver is either the business owner or an active staff member whose effective action permission for approve_requests is Allowed. Merely being active staff is not sufficient. Owner decisions are attributed directly to the owner user ID even if the owner has no staff-membership row.

Existing handlers that still throw APPROVAL_REQUIRED from inside their SQLite transaction should be migrated to this runner pattern before they are treated as implementation-ready.
