Local SQLite + Sync Schema v1

Mobile-first database proposal for Khaata PG V1. This closes the missing half of the architecture: the app operates from SQLite, then synchronizes to Supabase.

Primary rule: normal business work commits locally first. Internet or Supabase availability is not required for everyday PG operation.
Status: proposed implementation schema. Product invariants are frozen; exact SQLite field names, sync transport and conflict-resolution algorithm are still implementation choices.

Architecture

SQLite is the operational source on the phone. UI/domain code writes SQLite first. Supabase is synchronized shared state, not a prerequisite for normal PG work.

Local-only infrastructure

sync_outbox, sync_checkpoints, applied_remote_events, sync_conflicts, device_state, entitlement_snapshot, local_settings and schema_migrations exist only on-device.

Offline IDs

All domain IDs are generated before sync. SQLite stores them as TEXT so the app can use one globally unique offline-safe ID format consistently across SQLite and Postgres.

Atomic payment write

A payment, its allocation(s), immutable receipt snapshot, optional staff cash-custody event, domain event and sync-outbox entries commit together in one SQLite transaction. The UI can show the tenant as paid immediately after the local commit.

Conflict policy

Financial/history-sensitive entities never use blind last-write-wins. Concurrent events are preserved; semantic conflicts are placed in sync_conflicts for explicit resolution.

Schema alignment

The mobile domain tables deliberately mirror the proposed Supabase/Postgres schema so mapping stays boring. Sync metadata remains local and is not treated as business data.

Runtime path

Khaata UI ↓ Domain / business logic ↓ SQLite transaction ├─ domain records ├─ immutable financial/history records └─ sync_outbox ↓ Background sync worker ↓ Supabase / Postgres Remote change ↓ sync pull ↓ SQLite transaction ├─ apply safe changes ├─ preserve concurrent events └─ create sync_conflicts when meaning cannot be merged safely

What the SQL includes

Mirrored PG domain tables; local sync metadata; WAL mode; projection views; immutability triggers; one-active-occupancy constraints; deterministic obligation keys; entitlement snapshot storage; outbox/checkpoint/conflict tables; and documented atomic transaction recipes for payments, transfers and security application.

Important consequence

If Ravi records a ₹8,000 cash rent payment with no internet, SQLite can commit the payment, allocations, receipt and Cash with Ravi custody event immediately. The tenant is paid immediately. Sync can happen later; a failed handover or discrepancy must never turn that tenant back into unpaid.
