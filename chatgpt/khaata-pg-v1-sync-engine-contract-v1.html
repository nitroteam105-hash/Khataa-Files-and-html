PG V1 Sync Engine Contract v1

Concrete sync behavior for the local-first SQLite ↔ Supabase architecture. This document defines the proposed runtime protocol, not the network transport implementation.

Core guarantee: Khaata writes locally first. A successful SQLite transaction is enough for the user to continue working immediately.
Entitlement rule: already-recorded outbound events must still drain after entitlement loss if they were created while entitled or inside valid offline grace.

1. Sync states

Normal

Pull remote changes, apply locally, then push pending outbox work. Future synced writes allowed.

Offline

All local-capable work continues. Outbox grows. UI may show pending sync state but does not block core operation.

Drain-only

Used after sync entitlement loss. Existing legitimate outbox entries may upload; future gated synced capability stays blocked.

Conflict

Automatic merge would destroy business meaning. Preserve local + remote facts and create an explicit conflict record.

2. Push algorithm

acquire sync lock ↓ load pending outbox rows ↓ sort by dependency + created_at ↓ send idempotent batch using client-generated IDs ↓ server result per item ├─ ACK │ ├─ mark domain row synced/server_version │ └─ mark outbox acknowledged ├─ RETRYABLE ERROR │ └─ increment attempt_count + backoff ├─ PERMISSION / ENTITLEMENT LOSS │ ├─ if event predates loss and was legitimately recorded → continue drain │ └─ otherwise block future gated mutation └─ SEMANTIC/VERSION CONFLICT ├─ preserve local state ├─ store remote snapshot └─ create sync_conflicts row

3. Pull algorithm

read sync_checkpoint.server_cursor ↓ fetch remote changes after cursor ↓ BEGIN SQLite transaction ↓ for each remote event/record ├─ already in applied_remote_events? → skip ├─ safe append? → insert ├─ safe mutable merge? → apply versioned update └─ unsafe semantic overlap? → create sync_conflict ↓ record applied_remote_events ↓ advance checkpoint ↓ COMMIT
Checkpoint rule: never advance the server cursor before the corresponding SQLite transaction commits successfully.

4. Merge policy by data class

Data classPolicy
Payments / reversalsAppend-only. Preserve every legitimate event.
ReceiptsImmutable snapshot. Duplicate delivery is deduplicated by ID.
Payment allocationsAppend-only effects; recompute projection.
Security eventsAppend-only; never infer automatic application.
Cash custody eventsAppend-only; discrepancy cannot rewrite tenant payment truth.
Occupancy historyPreserve assignments. Same-capacity overlap creates explicit conflict.
Rent termsEffective-dated. Non-overlapping changes can coexist; incompatible overlap requires resolution.
Business/profile fieldsVersioned mutable merge is acceptable where history is not semantically critical.
Permissions/visibilityVersioned snapshots; action permission and offline cached-data access remain separate.

5. Idempotency contract

Every locally-created syncable object gets its final globally unique ID before network access. The server must treat re-sending the same ID as the same operation rather than creating a duplicate. Outbox retries therefore remain safe across process death, network timeout, app restart and uncertain ACK delivery.

6. Ordering rules

DependencyRequired order
New business + tenancyBusiness before tenancy.
Tenancy + role assignmentsTenancy/party before role assignment.
Charge + charge obligationCharge before obligation referencing it.
Payment + allocation + receiptPayment before allocation/receipt.
Security account + eventSecurity account before security event.
Approval + action executionApproval decision can precede the separately recorded action event; they remain distinct.

7. Backoff / retry

Proposed policy: retry transient failures with bounded exponential backoff plus jitter. Reset backoff after any successful sync. User-triggered “Sync now” may bypass waiting once, but must not create duplicate work.

8. Entitlement-sensitive sync

The device keeps a last-verified entitlement snapshot. Paid access may continue offline within the configured grace period. When grace expires, future paid-only capability falls back to the effective Free set. However, outbound events already recorded while valid remain uploadable. This is a distinct drain-only mode: the queue empties, historical truth remains intact, but new gated synced work is not allowed until verification succeeds.

10. What is still open

Exact wire protocol, batch size, realtime transport, background-job scheduler, ID format (UUID/ULID/etc.), conflict-resolution UI, and server RPC shape remain implementation decisions. The product requirement is the behavior above, not a specific library.
