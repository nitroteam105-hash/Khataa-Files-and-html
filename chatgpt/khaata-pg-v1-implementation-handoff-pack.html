PG V1 Implementation Handoff

Canonical product contracts for building the frozen PG / Hostel V1. This is a handoff specification, not a database schema.

Status: structurally frozen.
The implementation must preserve the product hierarchy, lifecycle rules, money model, navigation, offline-first behavior and exception semantics. Visual refinement and internal architecture can still evolve.

Build map

Recommended implementation slices, ordered to protect the core invariants first.

1. Business + property shellBusiness identity, one operational currency, Building/Block → Floor → Room → Bed/capacity. Property setup creates capacity only; tenancy commercial terms are separate.
Foundation
2. Tenancy lifecycleUpcoming → joined/active → planned move-out → end tenancy → Former, while preserving occupancy history and future commitments.
3. Obligation + payment engineDeterministic monthly obligations, many-to-many payment allocation, receipts, credit, arrears and statements.
Critical
4. Security + corrections + chargesSecurity held, refunds, explicit application to dues, immutable receipts, reversals/corrections, disputes, waivers and write-offs.
5. Expenses + staff cash custodyBusiness-paid vs staff-paid expense accountability; tenant settlement remains separate from physical cash custody/handover.
6. Staff & permissionsOwner, Manager, Caretaker / Front desk, Accounts; action permission and visibility remain separate.
7. Backup, entitlements and syncLocal-first operation, explicit conflict handling, named entitlement gates, offline entitlement snapshot.
8. UI shellHome · Tenants · Collections · More with global FAB: Add tenant · Record payment · Add expense · Add charge.
Source-of-truth rule: when a prototype conflicts with the frozen PG Product Structure, the frozen specification wins. Visual-system sources govern visual treatment only.

Lifecycle rules
Future tenants remain Upcoming until explicitly confirmed joined.
Missing joining date does not auto-cancel the tenancy or release the bed.
Room transfer preserves old occupancy history; new assignment begins separately.
Planned move-out is not the same as tenancy end.
Former tenant receivables and pending refunds remain discoverable.
Capacity with history is retired/archived, not hard-deleted.

Money contracts

The financial model is event/history based. Posted financial history must not be destructively rewritten.

Monthly obligationsActive rent agreements deterministically create monthly calendar obligations. Billing timing is prepaid/postpaid; due-day changes are prospective.
AllocationOne obligation can receive many payments; one payment can settle many obligations. Excess becomes credit. Old dues remain distinct from current dues.
ReceiptsImmutable snapshots of real payment events. A mistake creates a new correction/reversal event.
SecurityNever silently settles arrears. Apply security to dues is an explicit action. Refund is separate money-out.
Charges and adjustmentsCharges are distinct from rent, payment and deposit. Waiver, discount, write-off, correction and dispute are not payments.
Cash custodyA valid staff cash collection settles the tenant immediately. Physical cash custody, handover and discrepancies are separate events.
Event chain
rent agreement → monthly obligation → payment event → allocation(s) → immutable receipt staff cash collection → tenant obligation settled → cash custody assigned to staff → handover event → optional discrepancy → discrepancy resolution wrong payment → original payment preserved → correction / reversal event security held → explicit apply-to-dues OR refund → never automatic

Access & entitlements

Permission policy and commercial packaging are separate layers.

Staff permissions
Action statesAllowed · Needs approval · Not allowed.
Visibility is separateA user may be allowed to perform an action without seeing every data area.
Approval requestAn approval request does not mean the action already happened. Approval grants authority; execution remains explicit.
Entitlement contract
Feature code checks stable entitlement keys, never tier names.
multi_user gates additional people/accounts and requires cloud_sync.
role_permissions gates configurable roles, visibility and action permissions; it requires multi_user.
drive_backup gates manual Google Drive backup/restore and does not require cloud_sync.
multi_device, auto_backup and cloud_restore require cloud_sync.
Tier-to-entitlement mapping is server-side configuration, not app logic.
Packaging note: current minimum-tier mapping is configuration and can change. Do not hardcode Free / Pro / Premium checks into feature code.

Offline & sync

Local-first is a product invariant, not merely a resilience feature.

Core work remains local/offline-capableBilling obligations and normal operating flows must not depend on live server availability.
Sync is separate from backupOn this device only, Google Drive backup and Khaata Sync are distinct operating choices.
Offline entitlement snapshotDevice stores effective entitlement keys, verification metadata, grace expiry and configuration/version identity.
Conflicts stay explicitDo not silently discard concurrent events or history. Exact sync protocol internals remain an implementation detail.

Acceptance QA

Minimum release checks for implementation fidelity.

Add Business carries name/type/location/currency into the PG workspace.
Both capacity setup paths work: preconfigure rooms and progressive inline creation.
Upcoming tenant cannot become active or release capacity merely because a date passed.
Room transfer preserves prior occupancy history and does not silently change rent.
Monthly obligations are deterministic and reproducible offline.
Partial/multi-allocation/excess-credit cases work without replacing history.
Payment correction creates a new event; original receipt remains immutable.
Security never auto-settles dues.
Staff cash discrepancy never makes a tenant unpaid.
Former tenant can still have outstanding balance and pending refund.
Permissions use Allowed / Needs approval / Not allowed; visibility is independently enforced.
Entitlements are checked by key and tier mapping is not embedded in feature code.
Top-level PG navigation remains Home · Tenants · Collections · More; FAB action set remains stable.
360px-wide rendering has no horizontal overflow; interactive targets are at least 44px.
Sheets/dialogs support Escape, focus entry, focus containment and focus restoration.
