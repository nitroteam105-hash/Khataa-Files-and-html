Staff Access Enforcement v1

This turns Staff & Access from configuration data into an executable authorization boundary for the mobile command layer.

Core rule: every protected command evaluates Allowed / Needs approval / Not allowed before mutating SQLite.
Approval remains two-step: approving a request creates an authorization. The actual business action still has to run later and consume that authorization inside its own transaction.

Approval execution path

staff attempts protected command ↓ AccessGate.requireAction(...) ↓ permission = Needs approval ↓ create approval_request ↓ STOP — no business mutation yet approver approves request ↓ create approval_authorization ↓ STOP — still no business mutation staff retries command with authorization ↓ validate actor + action + target + unused authorization ↓ perform domain mutation ↓ append domain event ↓ consume authorization in SAME SQLite transaction ↓ COMMIT

Missing tenant requirements

tenant has missing Required item ↓ RequirementService reports Setup incomplete ↓ base command permission check ↓ AccessGate checks: proceed_with_missing_requirements ├─ Allowed → proceed, Setup incomplete remains visible ├─ Needs approval → request approval and stop └─ Not allowed → stop Requirement policy itself is never changed by this decision.

Storage added

staff_roles, normalized role action permissions, visibility rules, area-access levels, property scopes, one-use approval_authorizations, effective-access views and append-only staff access history. Default role-template contents remain configurable rather than being invented as frozen product policy.

The included test matrix covers owner-only operation, each permission state, approval creation vs execution, authorization reuse, disabled staff, missing-requirement override, visibility separation and target-bound approvals.
