Supabase Typed Domain RPCs v1

The generic server sync envelope now has concrete typed handlers for the highest-risk PG operations.

Server validation now mirrors the local domain layer: each RPC accepts client-generated offline IDs, re-checks permission and business invariants, writes one atomic server transaction, and records an idempotent sync result.
Still not applied to Supabase. This is a proposed migration and should be reviewed against the actual project schema before execution.

Payment path

offline SQLite payment ↓ outbox reconnects ↓ pg_record_payment(...) ↓ same operation_id already accepted? ├─ yes → return prior ACK └─ no ↓ business + action authorization ↓ validate tenancy + allocations ↓ payment_event + payment_allocations + immutable receipt_snapshot + optional cash custody + domain_event ↓ consume one-use approval if applicable ↓ store sync ACK

Approval integration

A Needs approval permission cannot be silently accepted during sync. The migration adds one-use server approval_authorizations. A typed domain RPC validates the actor/action/target, performs the real business mutation, writes its domain event, and only then consumes the authorization.

Drain-only sync

The active entitlement rule requires already-legitimate outbound events to drain even if cloud_sync is lost before reconnection. This build adds server storage for verified entitlement/grace epochs, but deliberately does not trust a client boolean such as “recorded while entitled”. The exact tamper-resistant offline proof design remains open and must be chosen before production rollout.

Why this matters

The mobile app and the server now enforce the same high-value boundaries independently. A compromised or buggy client cannot use the generic sync layer to mutate payment history, silently change rent during a transfer, auto-apply security, or turn a cash discrepancy into an unpaid tenant.
