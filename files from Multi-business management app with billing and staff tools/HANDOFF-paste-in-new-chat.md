## Decisions made this session

### 1. Tier structure (revised)
- **Free**: unlimited businesses, all core features, local-only, single device, no ads
- **Paid Pro**: cloud sync + multi-device + auto-backup/restore + bill themes/branding
- **Paid Premium**: multi-user/staff access + advanced reports/analytics + priority support
- Business count is NOT a gating lever (conflicts with core multi-business positioning). Gating is on sync, multi-user, and feature depth instead.

### 2. Business Settings — Business Profile
- 3 depth presets: **Simple** (name, phone, business type) / **Standard** (+logo, address, GST toggle) / **Detailed** (+GSTIN, registered legal name, state, bank/UPI for invoice footer)
- GST toggle **auto-suggested** based on business type (Mode 2/job-service → default ON; Mode 1/subscription → default OFF), owner can override

### 3. Business Settings — Operational Rules
- **Payment Modes**: fully customizable list per business; multiple UPI IDs per business, each labeled (e.g. "Main collection," "Rent account")
- **Invoice Numbering**: Prefix + Year/Month + auto-increment (e.g. PGA-2026-0001). Owner chooses sequence scope: shared across all businesses / separate per business / separate per business per financial year
- **Tax Rates**: preset GST slabs (0/5/12/18/28%/Exempt) + owner's own saved HSN/SAC code + rate pairs, reusable via dropdown. **No built-in official HSN database** (avoids stale-data compliance liability). Optional post-MVP: reference link to GST portal, not auto-applied
- **Due-Date Defaults**: business-level default (e.g. 7/15/30 days) + optional per-customer-type override (e.g. B2B vs walk-in)

### 4. Business Documents section
- Suggested common types (GST Certificate, Shop License, Rental Agreement, Fire Safety NOC, etc.) + custom labels
- Storage: Google Drive (BYOS)
- Viewer: single clean full-screen mode (no separate "showcase mode" — the default viewer IS clean/full-screen)
- Document card shows friendly label (main) + actual filename + file type as meta
- File types: PDF, Images, Word/Excel, with fallback for unsupported types
- Actions per document: **View, Download, Share** (all three)
- **Secure Showcase lock**: global default toggle ("require unlock to exit document view") + per-business override. Uses device-native biometric (fingerprint/Face), PIN as fallback only if no biometric hardware. Off by default.

### 5. Multi-Business Setup Status page
- After "What do you run?" (business type multi-select), shows a status page: each business as a card with progress %, Done/Pending badge, Edit/Continue button
- **100% complete = required Business Profile fields (per chosen preset) + at least one Payment Mode set.** Optional fields (GSTIN, bank details, custom tax rates) don't block 100%.
- "Go to Dashboard" always available, even with pending businesses
- Pending businesses tracked via a **side drawer (☰ hamburger menu)**: shows avatar/logo, "My Businesses" list with Done/Pending status + Edit icon per business linking directly back into that business's setup — no nagging banner

### 6. Business type selection — info popups
- Each business type tile gets an **ⓘ info icon** — tap opens a bottom-sheet popup with: one-line description, concrete example, and which billing Mode it maps to (Mode 1 subscription vs Mode 2 job/service)
- Descriptions drafted for all ~14 types shown in Replit prototype (PG, Gym, Tiffin, Coaching, Flat, Hostel, Parking, Co-living, Saloon, Hardware, Tailoring, Bakery, Clinic, Dairy) — Saloon/Clinic/Dairy mode assignments are best-guess, worth revisiting

### 7. Coaching / Gym / Yoga — deep-spec (schedule-based businesses)
**Note: Coaching needs its OWN separate setup (see below) — do not merge with Gym/Yoga.**
**⚠ Superseded by section 11 (Timetable): this section and the existing `gym-yoga-setup.html` mockup still show "Trainer: Priya" hardcoded on batches — that's now outdated. Instructor/Trainer assignment should be removed from Gym/Yoga batch setup too and moved to the Timetable page, same as Coaching. Not yet updated in the mockup — revisit next session.**

- **Schedule Module** (Gym + Yoga): Access type = Open-access / Batch-based / Hybrid
  - Open-access: operating hours only (owner can add multiple day/time ranges, e.g. Mon–Sat one range + Sunday a different range, via "+ Add Hours")
  - Batch-based: one+ batches, each with day(s), time slot, capacity, instructor/trainer
  - Hybrid: operating hours + optional special batches (e.g. gym open all day + 6 AM Zumba class)
- **Batch mode (per batch, not per business)**: Offline / Online / Hybrid
  - Studios commonly mix — e.g. a 6 AM hybrid batch + a 7 PM offline-only batch — so mode must be set per batch, not once for the whole business
  - Online/Hybrid batches show an **optional** meeting link field (not required); if filled, can auto-include in student reminders, otherwise owner shares manually
  - Offline batches show physical location / inherit business address
- **Multiple continuous/overlapping sessions**: two view modes
  - **List view** (for setup): grouped by day, sessions in time order — used when adding/editing batches
  - **Calendar/timetable view** (daily glance): sessions laid out on a time grid, parallel sessions shown side by side
- **Rooms/halls**: optional — only relevant if a studio has more than one space
  - Single-space studios: no room field, sessions just run back-to-back
  - Multi-space studios: owner enables rooms, each batch gets a room assignment, room becomes a lane/column in the calendar view (lets two batches run at the same time without clashing)
- **Fee Module (v1, revised — replaces flat toggle list)**:
  1. **Fee Plans** — owner creates named plans (e.g. "Beginner Yoga," "Advanced Yoga," "Kids Yoga," "Personal Training"), each linked to one or more batches. Each plan has multiple billing cycle options (Monthly / Quarterly / Half-Yearly / Yearly / Custom duration), each cycle with its own price (not just monthly×N — allows built-in discount for longer commitment)
  2. **Trial Session** — free or paid, offered before a customer commits to a plan
  3. **Membership Freeze/Pause** — pause billing for a period (e.g. travel), resumes after
  4. **Add-on Charges** — locker, diet consultation, merchandise, etc. — separate line items from the core plan fee
  5. **Discount** — manual field, applied per customer at onboarding time (flat ₹ or %), owner's discretion — no automated bundle/late-fee rule engine in v1

### 9. PG / Hostel / Co-living — deep-spec

- **Building Layout** — depth preset (Simple/Standard/Detailed), same pattern as other modules:
  - Simple: flat room list, no floors/blocks
  - Standard: Floors → Rooms
  - Detailed: Blocks → Floors → Rooms (multi-building/wing properties)
  - Rooms support bulk range creation (e.g. "101 to 110" auto-generates 10 rooms; alphabetic ranges like "Block A to D" also supported) with a live preview before confirming, plus single-add mode. Remove buttons at every level (room/floor/block), floor/block deletion asks for confirmation since it removes everything nested inside

- **Amenities & Add-ons** — same extensible pattern as Gym add-ons: suggested common items (Food [Veg/Non-veg/Not provided, Included-or-Separate charge], WiFi, Study Room, Housekeeping, Laundry, Parking [2-wheeler/4-wheeler, separate fee]) + ability to add custom amenities. Each toggled on/off, with editable fee if "separate charge"

- **Facilities & Compliance**: power backup (Y/N), water supply (24/7/Timed), CCTV/security (Y/N), police verification required (Y/N)
  - **Cross-module dependency**: if Police verification = Yes, this should auto-require ID proof in that business's Customer Intake Template (overriding the usual optional/toggleable default)
- **Security Deposit** — NOT fixed at business or room-type level. Fully custom, entered per tenant during Customer Intake/onboarding

### 11. Timetable (NEW — separate page, not part of onboarding) + Attendance toggles
- **Timetable is its own page**, separate from business setup/onboarding — scoped **per business, and only shown for schedule-based business types** (Gym/Yoga, Coaching — i.e. types that have batches)
- This is where **Instructor/Trainer assignment actually happens** — batches are created without an instructor during setup; the Timetable page assigns staff (pulled from the real Staff module, not free text) to time slots
- **Solo owner-operator exception**: a single owner-teacher (e.g. home tutor) is auto-available as the instructor without needing to go through Staff onboarding first — forcing self-onboarding as "staff" just to assign yourself to your own batches is unnecessary friction for a one-person business
- Should check for **double-booking conflicts** (same instructor already assigned to an overlapping day/time in another batch) — **built and tested** in `timetable.html`: soft warning only (flags both rows + banner), doesn't block saving. Conflict logic compares shared day + overlapping time range (simple regex-based time parser) + same instructor, computed **per selected day** (not globally across the week)
- **Room and Day are both first-class filters/dimensions**, not just metadata — added after stress-testing against a 10-room coaching centre scenario. List view has a Room filter; Calendar view shows rooms as side-by-side lanes; a Day selector (Mon–Sun) sits above both, since a real schedule's room/subject/instructor assignments can differ entirely from one day to the next (e.g. MWF vs TTh rotations) — the mockup's sample data intentionally varies by day-group to test this, and correctly shows "no classes" on days with nothing scheduled
- **Conflicted rooms are visually flagged red** (with ⚠) directly on the Room filter pills and on Calendar room labels — lets the owner spot problem rooms at a glance without checking each one; updates live as instructors are reassigned
- **Attendance tracking has two independent Yes/No toggles**, not one combined switch — both now visualized side-by-side in `coaching-setup.html`'s Attendance tab:
  - **Track Student Attendance** (per business, relevant for Coaching/Gym/Yoga) — if off, the Student Attendance feature stays off for that business
  - **Track Staff Attendance** (per business, applies to any business with staff) — fully independent of the student one

### 12. Individual/1:1 sessions (home tutor case) — decision: reuse Batches, don't build a parallel model
- Considered a separate 1:1 session model (vs. group batches) for home tutors/solo operators with rotating individual students across mixed subjects/grades — **rejected** in favor of reusing the existing Batch model, to avoid maintaining two parallel systems across Schedule/Fee Plans/Attendance/Timetable that could drift out of sync
- **Capacity becomes optional, not required**, on a batch — if left blank (or set to 1), the batch is effectively an individual session (e.g. "Ravi — Math, Grade 8, Mon 4–5pm, no fixed capacity"), same mechanism as a group class, just naturally smaller
- Not yet updated in `coaching-setup.html` mockup — Capacity field should be relabeled/treated as optional there too
- **Considered and skipped**: an explicit "type of coaching" selector (Home Tutor / Regular Tutor / Coaching Centre) at setup. Rejected — the flexible model (optional Grade, optional Capacity, auto-grouping by Subject, solo-operator auto-instructor) already adapts to all three without needing to know which one it is upfront; forcing a label risks going stale as a business grows (e.g. solo tutor hires a second teacher)
- **Considered and skipped**: Mark Card/report card generation (exam scores, grading, academic report cards) for Coaching. Rejected entirely — it's academic assessment tracking, a fundamentally different domain from Khaata's record-keeping/money-recovery positioning, only serves 1 of ~14 business types, and is a large standalone feature (exam definitions, grading scales, PDF report layouts) that risks pulling solo-dev focus away from the core wedge

### 14. Vasooli / Daily Follow-up List — deep-spec (shared infrastructure, first prototype)
- **Scope**: per-business (owner switches business first, sees that business's list — not a unified cross-business view)
- **Sort order**: owner-selectable — Oldest first (days overdue) / Highest amount first / Urgency (days × amount combined)
- **Three item types** surfaced together in one list, each visually badged: **Unpaid Due**, **Unanswered Quote**, **Unrecovered Advance** — unifies both business modes without new data infrastructure, as originally conceived
- **Actions per item** (kept to exactly two, deliberately simple):
  - **WhatsApp Reminder** — tap to preview the actual pre-filled message before sending (type-specific wording: dues include a UPI deep link, quotes are a soft follow-up nudge, advances are a plain reminder). Message preview toggles open/closed on repeat taps

### 15. Bill Themes/Branding — deep-spec (Paid Pro feature, 5 themes built)
- **Reframed monetization logic**: Free tier = 1 simple universal bill (generic item table, no business-awareness). Paid Pro = business-specific tailored bill templates, auto-matched to business type rather than a cosmetic pick — the pitch is "a bill that's actually smart about your business," not just prettier colors
- Architected as **full swappable layout templates**, not color-only skins — proven across 5 structurally distinct themes, each with its own signature visual device and accent color for quick recognition
- **Theme 1 — Classic Professional** (green accent; services: Clinic, Saloon, Tailoring per-order, Coaching when billed per-visit): ribbon bar + overlapping circular logo badge, two-column header, simple items table, GST summary box, UPI QR, signature line
- **Theme 2 — Shipment** (green accent; goods/transport: Hardware): full-width colored banner header, invoice-meta strip (Vehicle No./E-Way Bill No.), side-by-side Bill-To/Ship-To, horizontally-scrollable wide items table (HSN/Qty/Rate/Taxable Value/GST%/GST Amt/Total), Freight & Packing charges, HSN-wise tax recap table, Bank details + UPI QR, Terms & Conditions
- **Theme 3 — Retail** (amber accent; simple over-the-counter goods: Bakery, Dairy): receipt-style — dashed top/bottom borders, centered rounded-square logo + business name, "Cash/Retail Invoice" tag, items shown with dotted-leader price rows + qty sub-line, simple Subtotal/GST%/Total, UPI QR, friendly thank-you footer. Deliberately skips all transport/consignee fields
- **Theme 4 — Subscription** (purple accent; recurring/period businesses: PG, Hostel, Co-living, Flat, Gym, Yoga, Tiffin, Coaching-on-monthly-plans, Parking-as-pass): colored "period hero" card up top spells out the cycle (Monthly/Quarterly badge) and explicit start–end dates (solves the Billing Period gap the other themes had), tenant/customer + plan name inline, carry-forward previous balance support. Perforated divider (✂) leads into a distinct **Payment Stub**: amount due, Pending/Paid status badge, due date, UPI QR
- **Theme 5 — Tally-style** (monochrome/black, no color; cross-vertical — works for any GST-registered business wanting the traditional look, built as a standalone theme rather than a cross-cutting toggle per owner's explicit choice): dense black-bordered compliance grid closely modeled on real Tally.ERP output, referenced against actual Indian GST invoice screenshots the owner shared. Seller/Buyer boxes, Despatch/Destination fields, items table with tax lines (Output CGST/SGST) as rows within the same table rather than a separate box, Amount Chargeable in words, separate HSN-wise tax summary table, Tax Amount in words, Bank Details + Declaration text, "for [Company]" signatory block, "Computer Generated Invoice" footer. Deliberately plain — its credibility comes from being instantly recognizable to Indian accountants/CAs, not from looking modern
- **Template selection follows the Fee Plan's billing cycle, not the business-type label** — e.g. a coaching centre billing monthly uses Subscription, while a home tutor billing per-session uses Classic Professional, even though both are "Coaching"
- Open question, not yet decided: should the owner ever be able to **manually override** which template applies (e.g. a Hardware store sometimes wanting the lighter Retail layout, or anyone wanting Tally-style regardless of business type), or should it be fully automatic with no manual choice?
- The 4 branded themes reuse Khaata's typography (Plus Jakarta Sans + Inter) and sit on white (not parchment); Tally-style intentionally breaks from Khaata's visual language since plainness *is* its value proposition
- **All business types now have a matching bill template** — this closes out the "list all businesses and match a theme" exercise from this session

### 16. Bill Input Form — deep-spec (feeds all 5 themes, generate/preview fully working)
- **One adaptive form**, not 5 separate ones — matches the app's established modular pattern (fields show/hide based on context, same as Coaching's preset tabs or PG's depth levels)
- **Layout picker** at top: auto-selects based on the business's Fee Plan billing cycle (per the section 15 rule — cycle determines template, not business-type label), but can be tapped to override for just that one bill
- **Common fields** (always shown): Customer name + mobile, Items list (add/remove freely; each item has Description/Qty/Rate/GST% with a live-calculated line amount)
- **Conditional fields per layout** (shown/hidden via the same toggle pattern used everywhere else in the app):
  - Subscription → Billing Period (start/end/cycle), Due Date, Previous Balance
  - Shipment → Ship-to-same-as-customer toggle (+ address if different), Vehicle No., E-Way Bill No., Transporter, Freight (₹) + Packing (₹)
  - Tally-style → Buyer Order No./Date, Despatch Document No., Despatched Through, Destination, Terms of Payment
  - Retail/Classic → no extra fields
  - GSTIN field appears for Classic/Shipment/Tally (GST-relevant), hidden for Retail (cash sale)
- **Totals card** recalculates live on every input change: Subtotal, GST, conditionally Freight+Packing (Shipment) or Previous Balance (Subscription), Grand Total
- **"Generate Bill" produces a real populated preview** — tapping it collects all form data and renders the actual selected theme's layout with real values substituted in (not a static mockup): customer name/phone flow into Bill-To, items populate the table with correct per-line GST, and theme-specific fields (vehicle no., billing period, despatch details, etc.) appear exactly where that theme expects them
  - **GST-rate grouping**: since the form collects GST% per item rather than HSN codes, the Shipment/Tally recap tables group and sum by **GST rate** instead of HSN/SAC (labeled honestly as "GST Rate," not HSN) — tested with mixed-rate items (e.g. some 18%, some 5%) to confirm correct grouping and summed amounts
  - **Amount-in-words**: built a proper Indian-numbering (lakh/crore) number-to-words converter for Shipment and Tally-style, which both need it
  - **"← Back to Edit"** returns to the form with all entered data intact; **"Share Bill"** placeholder button sits on the preview screen
- Business identity (Sunshine PG) stays constant across all 5 rendered previews regardless of which layout is chosen — demonstrates that layout choice is a per-bill override, not a business re-identity
- **Editability audit fix (session follow-up)**: caught that most preview text was actually hardcoded, not wired to any input — fixed:
  - **Bulk GST% control**: "Set GST% for all items" dropdown + "Apply to All" button above the items list, so the owner doesn't have to set each item's rate individually. Still overridable per-item after
  - **Common "Bill Details" card** (Invoice No., Date) — previously hardcoded as "SPG-2026-0142" / "14-Jul-2026" in every single render function; now editable and actually flows into all 5 previews
  - **Common "Notes" field** — appears contextually as the footer note (Classic/Retail) or terms line (Shipment) in the rendered bill, so per-bill instructions like "pay by cheque only" actually show up
  - **Tally-style was missing real fields, not just unpopulated ones**: Delivery Note, Delivery Note Date, Supplier's Ref, Other Reference(s) had no corresponding inputs at all (shown as blank "—" with nothing behind them) — all four added. Declaration text was also hardcoded boilerplate — now editable
  - **Deliberately NOT made per-bill editable**: business identity (name/address/GSTIN), UPI ID, bank details — these come from Business Settings (set once, reused across all bills for that business), consistent with how the rest of the app avoids re-entering business-level config per transaction

### 19. Dairy — deep-spec (business-type coverage, mostly reuse)
- **Two independent modes**, at least one on, both can run together: **Home delivery** (recurring, billed monthly) and **Walk-in retail** (over-the-counter, billed per visit) — same toggle pattern as Clinic's appointment booking
- **Delivery quantity is usually fixed per customer** (not day-to-day variable) — confirmed by owner — so delivery products reuse the **existing Fee Plans model as-is** (e.g. "Cow Milk 1L Daily — Monthly ₹1,500"), no new billing infrastructure needed. Bills use the Subscription theme
- **Retail items reuse the existing Retail bill theme's** simple rate-list concept (Paneer, Ghee, Curd tub, etc.) — one-off pricing, no subscription
- **Skip-a-day** (the one genuinely new piece, and correctly scoped as **operational, not setup** per the established onboarding-vs-operational principle): each delivery product's per-day rate is auto-computed (Monthly amount ÷ 30), and marking a customer "Skipped" for a day credits that per-day amount toward their next bill — tested with two different products (₹1,500/mo → ₹50/day credit, ₹600/mo → ₹20/day credit), confirming the calculation generalizes correctly per-product, not hardcoded
  - **Refined after feedback**: real skip requests usually come in *advance* ("skip tomorrow"), not same-day — so the tracker has **two independent controls per customer**: today's actual Delivered/Skipped status, and a separate "Skip Tomorrow" toggle for pre-booking a skip when a customer calls ahead. Tested that the two states don't interfere with each other (can mark tomorrow's skip while today's delivery is still happening normally)
  - **Extended further for vacations/longer absences**: added a third mechanism — "+ Skip a week/month" opens a date-range picker with a live preview (day count + total credit as dates are chosen), confirms into a "⏸ Paused" badge showing the range/days/credit with one-tap cancel, and validates end-after-start. All three skip mechanisms (today's status, tomorrow's flag, date-range pause) coexist independently per customer — tested together without conflict
- **Extra items**: "+ Add extra item" per customer (e.g. a customer wants an extra litre or some paneer on a given day) — small form (description + ₹ amount), confirms into a green "+ Extra" badge; multiple extras per customer supported and stack, each individually removable. Tested coexisting with skip-tomorrow and a range-pause on the same customer simultaneously with no conflicts

Tested at full 45-customer scale across 4 areas, including the empty-results state when a search/area combination matches nothing. Sample data generated programmatically (name/area/product rotation) rather than hand-written, same approach as Timetable's 10-room stress test
- **Customer Onboarding** (`dairy-intake.html`, new — closes the loop with the area filter above): Name+Mobile required, **Area as a select-or-add hybrid** (tappable chips of areas already in use, but still free-text for a brand-new one — no separate managed-list screen needed; new areas typed here automatically join the chip list for the next customer, tested end-to-end), optional delivery address, **Customer Type** (Delivery / Retail only / Both) which shows/hides the product-selection step accordingly, product picker pulling from the same delivery products configured in Dairy Setup. Retail-only customers skip product selection entirely. Tested across all three customer types plus the save/reset flow
- Almost the entire spec was reuse of prior work — the only new things were the dual-mode toggle and the skip-day credit mechanism
- **UX upgrade**: "+ Add Product" and "+ Add Retail Item" were originally prompt()-based (same pattern PG's room builder started with); upgraded to proper inline forms (Confirm/Cancel), with opening one form auto-closing the other. Editing an existing item's price still uses a quick prompt, consistent with several other setup screens
- **Simplified back to a single step** (after briefly trying a two-step Item-catalog → select-item-to-build-plan flow, which added more structure than needed for this use case): "+ Add Product" now collects Name + Quantity + Unit (Litre/ml/kg/g) + **Price per day** in one form. **Daily price is the actual source of truth**; the monthly figure shown on each card is auto-computed (daily price × actual days in the current month) and labeled as an estimate — editing the daily price live-recalculates it. This is more honest than a flat manually-typed monthly amount, since it now naturally reflects the same day-count-aware precision fix already applied to skip credits, and daily-price-as-source-of-truth is a more accurate model for a business that's genuinely billed per day delivered
- **Precision fix — real months aren't all 30 days**: the original per-day rate calculation flatly divided monthly amount by 30, which is wrong for 28/29/31-day months and would cause small but real billing disputes over time. Fixed properly across all three skip mechanisms: today's credit and tomorrow's credit each use the actual day-count of their respective month (handles month-boundary skips correctly, e.g. skipping July 31 uses July's rate, not August's), and range/vacation pauses sum each individual day's own correct per-day rate rather than multiplying a flat rate by day-count — since a pause can span two months with different lengths. Verified with a real cross-month test (Feb 25–Mar 3, spanning a 28-day and a 31-day month) matching an independently hand-calculated total exactly. Also correctly handles leap years (Feb 29 in leap years vs Feb 28 otherwise)

  - **GST applies differently** — commercial rent is normally taxable, residential generally isn't; should inform default Bill Generation behavior per property type (not yet implemented)
  - **TDS (tax deducted at source)** — commercial tenants often deduct TDS on rent above a threshold before paying, meaning the owner receives less than gross rent and needs to reconcile against a certificate. **Left explicitly open — not yet decided** whether this is in scope or should be flagged out-of-scope like the e-signing feature; revisit after seeing more of the design
  - **Different unit types and onboarding fields** (Shop/Office/Warehouse/Showroom vs. Flat; trade license/GST registration capture at commercial tenant onboarding) — the unit type piece is built; the onboarding-field piece is not

Simple in-app e-signing doesn't satisfy stamp duty/registration, which are separate, state-specific processes usually requiring licensed e-stamping vendors (e.g. SHCIL). ## Key learnings & principles (carry into every session)

- **Onboarding/setup screens configure; they don't populate with real data** — during business setup there's no staff or customers yet, so setup screens should only contain config toggles/defaults (e.g. "Track student attendance: Yes/No"), never a working list of real names to mark/manage. Any screen that shows actual staff/customer records and lets you act on them (mark attendance, assign to a slot) is a **day-to-day operational screen**, built and shown separately, after onboarding. Caught this because the first Coaching Attendance mockup wrongly showed sample student names with mark-attendance buttons inside the onboarding flow — fixed to just a toggle.
- **Business-type setup is modular, not shared** — each business type (PG, Gym/Yoga, Coaching, etc.) gets its own self-contained setup module: its own fields, fee logic, and customer intake defaults, sitting on top of a shared Base Profile (name/phone/GST/payment modes/etc.). New business types are added as new modules without touching existing ones' code — protects against hardcoding early types in a way that's painful to extend later.
  - Data-model implication: common fields live in one shared structure; type-specific fields (PG's room layout, Gym's batches, Coaching's school/grade) live in a flexible per-type structure. Onboarding UI renders whichever module matches the selected business type.
- **Multi-step wizard is the preferred pattern for long operational intake forms** (registering a real customer/member/patient with many fields), over a single scrolling page of stacked cards — progress dots, one focused topic per screen, a "save now, add rest later" skip escape hatch, and a final review step before committing. Established via Coaching's rebuild (section 18); worth retrofitting to other business types' intake forms (PG tenant, Gym member, Clinic patient) rather than treating it as Coaching-specific
- **⚠️ VERY IMPORTANT — permission granularity via page-splitting, not permission-level complexity**: when a page or feature has an action that's meaningfully riskier than the rest of that page (delete, void, cancel, salary/hire-fire, etc.), **split that risky action out into its own separate page entry** in the access checklist, rather than building a 3-tier permission system (View/Write/Manage) as a feature. Keep the underlying permission model dead simple — just **View-only vs. Can Edit** — and let the *existence of the split-out sensitive page* do the work of creating a third, more privileged tier. Concretely: "Customers" (View or Edit) + a separate "Customers — Delete Records" (binary, sensitive) checkbox reproduces the full View → Edit → Manage spectrum without ever needing a 3-option selector anywhere. This was a deliberate choice over a "proper" RBAC system: full 3-tier permissions were considered and rejected as unnecessary complexity for Khaata's actual target audience (small business owners with a handful of trusted staff, not enterprise IT admins) — "Write-only" as a distinct middle tier rarely holds up in practice anyway, since someone who can add a record usually also needs to fix their own mistake. **Apply this same split-page pattern to every future business-type page that has a risky action** — don't reach for permission levels as the solution; reach for splitting the page
